Why orchestration

One provider is a single point of failure. Several, unmanaged, are a maintenance burden.

Orchestration puts a routing and management layer between your systems and your providers. You integrate once, add or replace providers by configuration, and let rules — not engineers — decide where each transaction goes.

ResilienceWhen a provider degrades or declines for technical reasons, traffic moves to an eligible alternative automatically.
Approval performanceRoute by issuer region, card type and method to the provider most likely to approve — and measure the result.
Cost controlPrefer lower-cost routes where approval performance is equivalent; see effective cost per route.
Negotiating leverageAdding or shifting providers becomes configuration, which changes the conversation with each of them.
Intelligent routing

Routing profiles you can read.

A routing profile is an ordered list of rules. Each rule matches on transaction attributes and names a primary provider plus an optional cascade chain. Profiles are assigned per merchant, group or tenant, and versioned so you can see what changed and when.

Shown: a readable representation of the rule model. The exact schema is documented in the API reference.

routing-profile: eu-cards-default · v7
// rule 1 — EU-issued cards, low valuematch: { issuer_region: "EU", amount_lt: 25000, method: "card" }
primary: "acquirer_a"cascade: ["acquirer_b"]
cascade_on: ["issuer_unavailable", "timeout", "do_not_honor_soft"]

// rule 2 — high-value, require 3DS challengematch: { amount_gte: 25000 }
require: { three_ds: "challenge" }
primary: "acquirer_a"// health policy — applies to all ruleshealth: { demote_when_error_rate_gt: 0.08, window: "5m", recover_after: "10m" }
Cascading & failover

Retry only when a retry can succeed.

Not every decline should be retried. Hard declines (stolen card, closed account) are final and retrying them harms your reputation with issuers. The engine maps each provider's response codes to a shared taxonomy and cascades only on retry-eligible outcomes.

Retry-eligible
Issuer unavailable / timeout
Technical failures between provider and issuer. Cascade immediately to the next provider.
Retry-eligible
Soft “do not honor”
Often provider- or path-specific. Cascade once; stop if the next provider agrees.
Final
Stolen / lost / closed
Never retried. Returned to the merchant with a normalised reason code.
Final
Insufficient funds
Not retried in the same attempt; eligible for scheduled retry in subscription flows.

FAQ

Payment orchestration: common questions

What is a payment orchestration platform?+

A layer that connects to multiple PSPs, acquirers and payment methods through one API, decides where each payment should go, and normalises the results into one set of reports.

How does smart payment routing work?+

Rules use inputs such as card country, currency, amount, card brand, merchant and risk score to choose the first route. Soft declines can cascade to another provider, and unhealthy providers can be bypassed automatically.

Does payment orchestration improve approval rates?+

It can, through local acquiring, disciplined retries on soft declines and failover during outages. The size of the effect depends on your traffic, so measure it on your own data.

Do I need to change my integration to add a provider?+

No. You integrate once with AQ Pay; new providers are connected and configured on the platform side and become available to your routing rules.
